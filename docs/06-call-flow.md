## 2. Generated dialplan shape

```ini
; ===== generated by Echelons — version 42 — sha256 … — DO NOT EDIT =====
[from-avaya]                                  ; trunk inbound context
exten => _X.,1,NoOp(Echelons inbound from AVAYA-PBX)
 same => n,Set(__ECH_PBX_ID=7c1e…)
 same => n,Set(__ECH_TRUNK_ID=a913…)
 same => n,Set(CDR(ech_pbx_id)=${ECH_PBX_ID})
 same => n,Set(CDR(ech_trunk_id)=${ECH_TRUNK_ID})
 same => n,Set(CDR(sip_callid)=${CHANNEL(pjsip,call-id)})
 same => n,Set(CDR(peer_ip)=${CHANNEL(pjsip,remote_addr)})
 same => n,Goto(ech-routes-7c1e,${EXTEN},1)

[ech-routes-7c1e]                              ; route table for PBX AVAYA, priority-ordered
exten => _95XXXXXXXX,1,Set(ECH_NUM=${EXTEN:1})
 same => n,Gosub(ech-route-apply,s,1(<routeId>,<patternId>,OUTBOUND,ALWAYS:MIXED:wav))
 same => n,Dial(PJSIP/${ECH_NUM}@CARRIER,60,${ECH_DIAL_OPTS})
 same => n,Hangup()
exten => _9XXXXXXXXXX,1,...
exten => i,1,...; invalid → CDR(ech_direction)=UNROUTED, Hangup(1)

[ech-route-apply]                             ; ARG1 route, ARG2 pattern, ARG3 direction, ARG4 recording policy code
exten => s,1,Set(__ECH_ROUTE_ID=${ARG1})
 same => n,Set(CDR(ech_route_id)=${ARG1}) ...
 same => n,Gosub(ech-record,s,1(${ARG4}))
 same => n,Return()
```

The exact generated text is produced by `packages/shared/src/dialplan/compiler.ts` and is
covered by snapshot tests. Pattern ordering follows Asterisk's own rules (it sorts by specificity,
not by file order). Because of this, Echelons **rejects ambiguous overlaps at the same priority** and
uses explicit specificity ordering in the matcher, so the app's dry-run tester returns exactly what
Asterisk would match.

## 3. Route-pattern semantics

The Asterisk pattern syntax is supported: `X` [0-9], `Z` [1-9], `N` [2-9], `[1-5a]` sets and ranges,
`.` one or more, `!` zero or more, and literal digits, `*` and `#`. The UI also accepts the `_` prefix
or leaves it out. The matching engine in `packages/shared/src/routing/pattern.ts` is shared by:
* the API dry-run tester,
* the CDR classifier (so historical calls reclassify consistently),
* the dialplan compiler (validation).

Precedence when several patterns match is (1) route priority (lower number first), then (2) Asterisk
specificity: more literal characters first, then a smaller character set per position, then a shorter wildcard.

## 4. Classification (post-call)

`classifyCall(ctx, rules)` evaluates enabled rules in `priority` order. Each rule is
`{conditions: all|any of [{field, op, value}], actions: {callTypeCode, routeId?, tags?}, stop}`.
Fields: `direction, sourcePbx, destPbx, trunk, context, callerNumber, destinationNumber,
destinationPattern, callerIsExtension, destinationIsExtension, disposition, billsec,
sipHeader:<name>, routeId`. Ops: `eq, neq, in, matches (route pattern), regex, gt, lt, exists`.

After the rules run, built-in status types are layered on top: `MISSED` (inbound + NO ANSWER), `BUSY`, `FAILED`,
`NO_ANSWER`, `ABANDONED` (queue exit before answer). They are stored as `answer_status` and are
also available as the type when no rule matched.
